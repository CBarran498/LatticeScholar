# 项目更新与政策运营手册

## 1. GitHub 项目如何持续更新

推荐使用固定闭环，而不是直接在线修改主分支：

1. 用户通过 Bug、功能建议或政策源 Issue Form 提交反馈；
2. 维护者确认问题、预期行为、隐私风险和验收标准；
3. 从主分支创建短期功能分支并修改代码；
4. 本机运行 `ruff check .` 与 `pytest -q`，界面改动再做浏览器验证；
5. 提交 Pull Request，由 CI 在支持的 Python 版本上重复检查；
6. 审核通过后合并，达到发布条件时更新版本和 Changelog；
7. 创建 `v0.x.y` 标签，Release 工作流构建包并生成 GitHub Release；
8. 已配置仓库地址的 LatticeScholar 会在账户页提示自托管用户新版本。

建议在 GitHub 启用主分支保护：要求 Pull Request、CI 通过和至少一次审核后才能合并。Dependabot 每周检查 Python、Docker 和 GitHub Actions 依赖更新。较大的产品方向先在 Discussion 讨论，避免 Issue 变成没有边界的愿望清单。

## 2. 版本策略

- `PATCH`：向后兼容的 Bug、安全或数据源适配修复；
- `MINOR`：向后兼容的新工作流、接口或页面；
- `MAJOR`：破坏兼容的 API、数据结构或部署方式变更；
- 每个 Release 必须包含升级说明、配置变化、数据库迁移影响和已知限制；
- 不把未验证功能描述成已完成，不把路线图放进“已实现能力”。

## 3. 政策自动发现的三种运行方式

### 本机手动

```bash
python scripts/sync_policies.py --source state-council
```

结果写入当前数据目录的审核队列。打开“系统管理 → 政策发现与人工审核”完成核验。

### 常驻服务定时运行

```bash
export LATTICE_POLICY_SYNC_INTERVAL_HOURS=24
export LATTICE_POLICY_SYNC_SOURCE_IDS=state-council,most,nsfc,moe
```

服务启动后按间隔发现候选。单次最多同步五个来源，避免给官方站点造成压力。

### GitHub Actions 健康监测

`policy-monitor.yml` 每天执行保守的 dry-run 并保存 JSON 报告，用于发现门户结构或网络访问是否失效。它不会把临时 Runner 上的候选直接发布到生产数据库；生产更新由常驻服务或管理员手动同步完成。

## 4. 管理员审核清单

每个候选至少核验：

- URL 是否为发布机构或权威转载机构的 HTTPS 官方页面；
- 标题是否为正式政策名称，而不是新闻、解读或栏目标题；
- 发布机构、成文/发布日期是否与原文一致；
- 文件是现行、试行、征求意见、废止还是历史版本；
- 摘要是否只概括原文，不加入模型推断；
- 政策信号是否与科研任务有关，标签是否不过度泛化；
- 是否需要记录地域、申报主体、有效期或配套细则限制。

批准后记录立即进入政策雷达；拒绝后保留状态以便审计。已批准条目若内容哈希变化，会重新回到待审核，不会静默覆盖。

## 5. 失败与恢复

- 某个政策源失败不会阻断其他来源，最近运行状态保存在数据库；
- 站点结构变化时，先更新对应解析规则和测试，再恢复定时任务；
- 不通过扩大抓取范围、绕过访问限制或模拟登录来“提高覆盖”；
- 数据库升级前备份数据目录；项目容器删除只解除证据归类，不删除证据内容；
- 发布出现回归时先撤回 Release 或发布修复版本，不改写已经公开的版本标签。
