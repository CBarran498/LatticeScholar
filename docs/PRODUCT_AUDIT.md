# LatticeScholar 全面产品审计与优化决策

版本：0.4.0  
审计日期：2026-08-04

## 1. 审计结论

0.3.0 已经证明“检索—分析—期刊—政策—Idea—证据库”可以在普通电脑上轻量运行，但它仍更像一组相邻工具，而不是科研人员可持续使用数月的工作系统。最大的缺口不是再增加一个生成按钮，而是缺少三个底层能力：

1. **研究上下文**：系统不知道一次检索属于哪个课题，用户过几周后也很难恢复当时的问题与范围；
2. **可复现轨迹**：结果可以收藏，但检索词、数据源、年份、缓存状态和运行时间没有形成可审计记录；
3. **可信更新机制**：政策是代码内静态快照，无法区分“自动发现”“人工核验”“正式发布”和“内容变化”。

因此 0.4.0 的产品主线从“功能菜单”改为“科研项目工作区”，并补齐可复现检索、项目证据归档、政策候选审核、题录导出、版本检查和开源维护基础设施。这些属于高频、低算力、低 Token、能够长期积累价值的能力。

## 2. 审计维度

每个功能都按以下问题检查，而不是仅检查“能不能运行”：

- **任务价值**：是否减少真实科研工作，而非增加一次看似智能的输出；
- **证据可信度**：结论能否回到 DOI、摘要片段或官方原文；
- **长期连续性**：一周后能否继续工作，换课题时是否会混淆；
- **可复现性**：他人能否知道用了什么检索条件、来源和时间；
- **隐私与合规**：是否绕过授权、保存不必要的全文或默认外发敏感内容；
- **资源效率**：普通 CPU、低内存和零模型配置下是否仍有主要价值；
- **失败可见性**：接口限流、字段缺失、政策过期和模型回退是否明确展示；
- **互操作性**：结果能否进入 Zotero、EndNote、其他分析工具或 Markdown；
- **可维护性**：数据源变化、用户反馈和版本发布是否有稳定流程；
- **商业公平性**：付费是否覆盖真实边际成本，而不是人为破坏社区版。

## 3. 问题清单与处理结果

| 优先级 | 审计发现 | 对科研工作的影响 | 0.4.0 处理 |
|---|---|---|---|
| P0 | 六个工作流没有课题容器 | 不同课题的查询、论文与 Idea 混在一起 | 新增科研项目、当前项目和项目状态 |
| P0 | 检索条件不留痕 | 无法复现查新范围或解释为何遗漏论文 | 保存检索词、来源、年份、数量、状态、耗时和缓存命中 |
| P0 | 政策快照只能随代码更新 | 时效弱，且自动抓取若直接展示会损害可信度 | 增量发现、内容哈希、版本记录、人工批准/拒绝、审核后发布 |
| P0 | 用户只能导出研究简报 | 难以进入 Zotero、EndNote 和写作流程 | 新增 BibTeX 与 RIS 导出 |
| P1 | 没有版本更新提示 | 自托管用户长期停留在旧版本 | GitHub Release 版本检查，6 小时缓存 |
| P1 | 用户反馈入口不结构化 | 维护者难以复现问题和判断需求 | Bug、功能和政策源 Issue Form，PR 模板 |
| P1 | 依赖与发布靠人工记忆 | 安全更新和版本发布容易遗漏 | Dependabot、CI、标签 Release 工作流、自动发布说明分类 |
| P1 | 检索时间只有起始年 | 历史综述与限定窗口不准确 | 增加截止年份和前后端范围校验 |
| P1 | 检索结果无法二次排序 | 新论文或高引用样本筛选效率低 | 支持相关性、最新发表、引用信号排序 |
| P1 | 删除项目可能被理解为删除证据 | 用户不敢管理课题 | 删除项目只解除归类，证据和检索记录保留 |
| P2 | 缺少系统综述去重、筛选与 PRISMA | 系统综述仍需在多个工具之间搬运 | 已列入下一阶段，必须先设计纳排标准和审计日志 |
| P2 | 缺少撤稿、更正与版本状态检查 | 可能引用已撤回或已更新证据 | 规划接入 Crossmark/PubMed 状态等合规来源 |
| P2 | 缺少跨论文证据矩阵与矛盾检测 | 多篇论文之间仍需人工逐表比较 | 规划本地结构化证据矩阵，模型只作可选归纳 |
| P2 | 缺少 Zotero/ORCID 双向同步 | 文献管理仍有重复操作 | 先提供开放导出，后续使用官方 API 或插件接口 |
| P2 | 缺少团队协作与细粒度权限 | 课题组无法共享项目又隔离未公开 Idea | 机构版方向；不能用单一共享密码替代权限模型 |

## 4. 0.4.0 的端到端科研路径

1. 用户先建立科研项目，写清项目名称、核心问题、已有资源和边界；
2. 当前项目显示在页面顶部，后续收藏默认进入该项目；
3. 文献雷达选择数据源、时间窗口和结果数，成功后自动记录完整检索条件；
4. 用户可按相关性、最新发表或引用信号重新排序，并导出 BibTeX/RIS；
5. 任意检索记录都可恢复为表单条件再次运行，便于查新复现；
6. 论文、政策、分析和 Idea 保存时与当前项目关联，项目页展示证据数量与最近轨迹；
7. 政策同步只创建待审核候选；管理员核验标题、发布机构、日期、官方 URL、摘要、信号和标签后才发布；
8. 账户页检查 GitHub 最新 Release，让自托管用户知道何时需要升级。

## 5. 算力、响应时间与 Token 设计

### 零 Token 路径

科研项目、检索历史、SQLite 证据库、题录导入/导出、政策同步与审核、规则分析、期刊样本聚合和模板化 Idea 均不调用模型。即使用户完全不配置 LLM，仍可完成主要工作流。

### 延迟控制

- 多个学术接口并发请求，单源失败不会阻断其他来源；
- 文献结果缓存默认 24 小时，项目 ID 不参与缓存键，避免相同查询因归档项目不同而重复消耗接口；
- GitHub 版本检查缓存 6 小时；
- 政策同步限制单次最多 5 个来源、单页 5 MB，并采用保守同域发现；
- 前端无构建链和大型依赖，页面仍由静态 HTML/CSS/JavaScript 提供。

### 模型使用边界

- 模型只用于需要跨证据推理的深度分析和 Idea 增强；
- 未配置模型时自动回退；
- 远程模型必须显式允许，且输入/输出有硬上限；
- 生成内容不会自动写成“已证实创新”或“政策要求”。

## 6. 政策自动更新为什么必须有人审

政府网站的栏目页会同时包含政策、解读、新闻、转载、征求意见和失效文件。仅凭网页标题自动发布会产生四类错误：把新闻当政策、发布日期解析错误、转载来源被误认为发布机构、内容变化后旧摘要继续展示。

当前机制采用四层防线：

1. 只从配置的官方门户发现链接，并默认限制在同一官方域名；
2. 保存外部 ID、内容哈希与原始发现信息，内容变化会重新进入待审核；
3. 审核时校验日期、HTTP(S) 官方 URL、摘要长度和结构字段；
4. 只有 `approved` 记录与人工维护的种子政策一起进入用户政策雷达。

这不是“完全无人值守”，而是把最耗时的发现工作自动化，把需要判断的发布责任保留给管理员。

## 7. 当前仍然诚实保留的边界

- 不宣称覆盖知网、Google Scholar 或 Web of Science 的全部内容；受限平台使用授权接口或用户合法导出的题录；
- 不提供影响因子、分区、审稿周期等无法稳定合法获得或需要机构许可的数据；
- 不把引用量当论文质量，不把期刊匹配分数当录用率；
- 不自动生成可直接提交的基金申请书或论文，不替代查新、伦理、统计与同行评审；
- 不对政策“全面、实时、绝对有效”作虚假保证；每条政策仍需查看官方原文与现行状态。

## 8. 后续路线图的决策门槛

下一阶段不按功能数量排序，而按以下门槛决定是否开发：

1. 至少有三个独立用户反馈指向同一高频任务；
2. 能定义可测试的正确性指标和失败提示；
3. 有合法、稳定且可维护的数据来源；
4. 零 Token 或本地能力仍能提供基础价值；
5. 不会鼓励伪引文、代写、绕过订阅或虚假成功率。

满足门槛后，建议顺序为：撤稿/更正检查 → 系统综述筛选与 PRISMA → 跨论文证据矩阵 → Zotero/ORCID 互操作 → 实验与数据管理计划 → 团队协作。
